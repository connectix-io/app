# Stay on MUI, upgrade it, and stop mixing

**Recommendation: keep this app on MUI and do not migrate to shadcn/ui in late 2026.** Instead, upgrade MUI 7 to MUI 9 and finish removing the half-adopted Tailwind/shadcn layer, so the app runs one design system with one way of handling right-to-left (RTL) layout. shadcn wins on two points that matter here: AI design tools (v0, Lovable, Figma Make) and raw LLMs produce shadcn by default, and in 2026 shadcn added first-class RTL support and moved to Base UI primitives. But neither point outweighs what this app already has: a working Hebrew/RTL setup, a five-theme MUI theme, larger touch-friendly controls for non-technical staff, and a codebase small enough that the stack choice is not the bottleneck. Published migrations succeeded when teams were already "fighting MUI" or juggling several design systems. That is not this app's situation, and the most common failure is a migration that stalls halfway and leaves two systems. MUI's real weaknesses for this app are the Emotion runtime cost, extra RTL setup work, and AI-tool friction. All three are manageable with a version upgrade and a few agent rules. Revisit only if the team starts building most new screens in v0 or Lovable, or if MUI drops Emotion in a future major. If a migration happens, the plan at the end keeps it incremental and reversible.

## What the repo actually looks like today

A quick audit of the working tree (2026-11-12) sharpens the question. **36 source files import MUI**: 44 `@mui/material` imports and 103 `@mui/icons-material` imports. RTL is set up in `src/context/DirectionContext.jsx` with two Emotion caches and the generic `stylis-plugin-rtl` package. Overlays are mostly Drawers (16 uses: the main menu and the softphone dock), plus Tables, Menus and Dialogs. **There is no Autocomplete, DataGrid or DatePicker**, which removes the hardest part of any migration and also any reason to buy MUI X licences. One finding stands out: **no file in `src/` uses a Tailwind utility class**, yet `src/index.css` still loads `@tailwind base/components/utilities`. In practice Tailwind contributes only its preflight reset, and that reset is known to clash with MUI. For example, it made MUI Button backgrounds transparent under Tailwind 3 ([Tailwind discussion #5969](https://github.com/tailwindlabs/tailwindcss/discussions/5969)). The app is therefore MUI-only in substance, with a leftover CSS layer.

One version fact changes the maintenance picture. **MUI skipped v8: v9.0 shipped on 8 April 2026 and the current release is 9.5.0** ([MUI v9 blog](https://mui.com/blog/introducing-mui-v9/)). So "staying on MUI" really means "upgrade from 7 to 9". The upgrade guide covers v7 to v9 directly ([Upgrade to v9](https://mui.com/material-ui/migration/upgrade-to-v9/)), and v9 is about 3% smaller than v7, makes `sx` up to 30% faster, and fixes accessibility issues ([MUI v9 blog](https://mui.com/blog/introducing-material-ui-v9/)).

### RTL is solved on both sides, but only MUI's is already paid for

MUI's RTL needs three things: `direction: 'rtl'` in the theme, `dir` on `<html>`, and an Emotion cache with the stylis RTL plugin. Two caveats: portal components such as Dialog **"don't inherit `dir` from their parents"**, and the Drawer swaps horizontal anchors under RTL ([MUI RTL docs](https://mui.com/material-ui/customization/right-to-left/); [Drawer.js source](https://cdn.jsdelivr.net/npm/@mui/material@9/Drawer/Drawer.js)). This app already handles both: it picks Drawer anchors from `isRTL` to keep the phone on the right. Icons are not auto-mirrored, and MUI's own scheduler swaps arrow icons with `useRtl()` ([mui-x PR #23955](https://github.com/mui/mui-x/pull/23955)). One newer gap: the plugin does not flip declarations inside `@container` queries ([PR #49739](https://github.com/mui/material-ui/pull/49739)). That is harmless unless the team starts using container queries.

shadcn's RTL is now first-class: **since January 2026, a CLI transform rewrites `ml-4`→`ms-4` and `left-*`→`start-*`, and adds `rtl:rotate-180` to icons** ([shadcn RTL changelog](https://ui.shadcn.com/docs/changelog/2026-01-rtl)). The result is architecturally simpler, because logical CSS mirrors at runtime and a he⇄en switch needs no cache swap. The approach still has rough edges. The automatic path only applies to projects made with `shadcn create`. Calendar, Pagination and Sidebar must be migrated by hand. Portalled Popover and Tooltip content needs an explicit `dir` ([shadcn RTL docs](https://ui.shadcn.com/docs/rtl)). And if the team chose the Radix base, Radix's `useDirection()` **ignores `<html dir="rtl">` without a `DirectionProvider`**, a bug closed "not planned" ([radix-ui #3830](https://github.com/radix-ui/primitives/issues/3830)). That matters for this app in particular: its header and phone panel are forced to `dir="ltr"` inside an RTL page, so each of those subtrees would need its own provider. Neither library removes the portal-`dir` chores. MUI's version of those chores is already written and tested here.

### Touch-friendly defaults matter more than a modern look for non-technical staff

shadcn's 2026 styles are tuned for dense desktop SaaS. **Nova's default button is `h-8` (32px) and new-york-v4's is `h-9` (36px)** ([style-nova.css](https://raw.githubusercontent.com/shadcn-ui/ui/main/apps/v4/registry/styles/style-nova.css); [new-york-v4 button](https://raw.githubusercontent.com/shadcn-ui/ui/main/apps/v4/registry/new-york-v4/ui/button.tsx)). Both pass WCAG 2.2 AA's 24px minimum but fall short of the roughly 44px platform guidance for touch ([Deque](https://docs.deque.com/issue-help/1.0.0/en/touch-size-small/)). MUI ships `SwipeableDrawer` with iOS-specific tuning ([MUI Drawer docs](https://mui.com/material-ui/react-drawer/)), and v9 stopped setting `aria-hidden` on Backdrop by default and improved roving tabindex in Tabs and menus ([MUI v9 blog](https://mui.com/blog/introducing-material-ui-v9/)). The Backdrop change matters for an inbox: a hidden app root can silence live announcements, such as an incoming call or message, while a dialog is open. Radix has exactly that open problem with live regions and toasts under dialogs ([radix #1820](https://github.com/radix-ui/primitives/issues/1820); [radix #4115](https://github.com/radix-ui/primitives/issues/4115)). shadcn's switch to Base UI, built by MUI engineers, as the default in July 2026 narrows the accessibility gap ([shadcn changelog](https://ui.shadcn.com/docs/changelog/2026-07-base-ui-default)). No independent head-to-head WCAG audit exists, and there is no user-testing data on which library non-technical users prefer. On touch density, MUI is the safer default and shadcn would need a deliberate size override.

## AI tooling is shadcn's one decisive advantage, and it is narrower than it looks

This is where shadcn clearly wins. **Lovable's official stack is React + Vite + Tailwind + shadcn/ui + Radix** ([Lovable FAQ](https://lovable.dev/faq/capabilities/tech-stack/lovable-tech-stack)), and third-party comparisons consistently describe v0 output the same way ([rework.com](https://resources.rework.com/tools/ai-coding/lovable-vs-bolt-new-vs-v0)). A May 2026 survey of default LLM stacks found **shadcn as the default for Claude, v0, Lovable and others in 5 of 9 tools, and MUI in 0 of 9** ([saschb2b.com](https://saschb2b.com/blog/llm-default-react-stack)). One tracker reports that Claude Code recommends shadcn in 90% of UI-component answers ([amplifying.ai](https://amplifying.ai/tech/mui)). shadcn's tooling also goes further: its MCP server installs real component source into the repo, and its Agent Skill reads `components.json` to learn the Tailwind version and primitive base ([shadcn MCP](https://ui.shadcn.com/docs/mcp); [shadcn Skills](https://ui.shadcn.com/docs/skills)). MUI's `@mui/mcp` only serves documentation, though MUI states its purpose plainly: stopping assistants from hallucinating links and APIs ([MUI MCP docs](https://mui.com/material-ui/getting-started/mcp/)).

The advantage is narrower than the headlines suggest. MUI's main AI failure mode is version drift, such as Grid's `item`/`xs` props replaced by `size` and component names changing across v5, v6 and v7 ([Grid v2 migration](https://mui.com/material-ui/migration/upgrade-to-grid-v2/)). Pinning the version in CLAUDE.md and adding `@mui/mcp` largely fixes that. shadcn has its own drift on two axes, Tailwind v3 vs v4 and Radix vs Base UI, and the shadcn Skill exists partly to counter it ([shadcn Skills](https://ui.shadcn.com/docs/skills)). No controlled benchmark of LLM accuracy on MUI vs shadcn exists, so accuracy claims either way are anecdotal. Consistency over time also favors MUI here. Because components live in a package, an AI session cannot quietly rewrite `Button`, while shadcn's copied-in code invites the drift RedMonk calls "the revenge of copypasta" ([RedMonk](https://redmonk.com/kholterhoff/2025/04/22/ui-component-libraries-shadcn-ui-and-the-revenge-of-copypasta/)). The practical cost of staying on MUI therefore falls mostly on one workflow: pasting v0 or Lovable output. If that is occasional, translating a mock-up into MUI with Claude Code is a small task. If it becomes the main way screens get designed, the balance tips toward shadcn.

## Bundle size, ecosystem and upkeep do not justify a rewrite here

The measured build puts the **MUI chunk at 113 KB gzipped, next to a 365 KB main app chunk**. So MUI is under a quarter of shipped JavaScript, and the app's own code is the bigger target. MUI estimates about **20 KB gzipped of fixed styling and theming overhead** ([MUI bundle guide mirror](https://www.mintlify.com/mui/material-ui/guides/minimizing-bundle-size)). Its zero-runtime successor, Pigment CSS, is **on hold**, so Emotion is staying for at least a year or two ([MUI: 2026 and beyond](https://mui.com/blog/2026-and-beyond/)). The headline migration savings, such as 1.8 MB down to 680 KB, come from a vendor case study with no methodology on a 120-screen app ([MetaDesign](https://metadesignsolutions.com/blog/migrating-react-app-from-mui-to-shadcn-ui-design-system-case-study)), and do not transfer to an app this size. A realistic gain from dropping MUI and Emotion here is tens of kilobytes plus less style work at render time in live-updating lists. That is worth having, but it does not decide the question.

Ecosystem is a wash for this app. It uses no Autocomplete, picker or grid. If it needs them later, MUI X's free MIT Data Grid and Pickers are there, with **Pro at $299 and Premium at $599 per developer per year** for advanced features ([MUI pricing](https://mui.com/pricing/)). shadcn offers free recipes over TanStack Table and react-day-picker, and its charts run on **Recharts v3, which the repo already ships** ([shadcn chart docs](https://ui.shadcn.com/docs/components/chart)). On maintenance, MUI ships a codemod-driven major roughly every 12–18 months (v7 in March 2025, v9 in April 2026). shadcn has no upgrades in that sense, but upstream fixes must be merged into your own copies by hand, and current shadcn assumes **Tailwind v4 with OKLCH tokens and `tw-animate-css` replacing `tailwindcss-animate`** ([shadcn Tailwind v4](https://ui.shadcn.com/docs/tailwind-v4)). This repo is on Tailwind 3.4 with `tailwindcss-animate`, so adopting shadcn means a Tailwind major upgrade first. On five themes, shadcn's model (named CSS-variable blocks such as `[data-theme="dim"]`) is simpler than MUI's, which only documents `light`/`dark` schemes out of the box ([MUI color schemes](https://mui.com/material-ui/customization/css-theme-variables/configuration/); [shadcn theming](https://ui.shadcn.com/docs/theming)). But the five themes already work in MUI.

## Migrations succeed when MUI is the enemy; this app's risk is stalling halfway

The first-hand accounts share one motivation. Thrive's MUI code was "mostly layers of overrides trying to make Material UI look like Thrive", spread across three competing libraries, and its strangler-fig migration took **about 18 months with 50+ engineers**. Its warning is blunt: **"An unfinished migration leaves you with one more design system than you started with"** ([Thrive](https://www.thrivelearning.com/blog-news/from-three-design-systems-to-one-our-migration-to-shadcn-ui)). Ambrook moved **794 files from MUI to Base UI in just over two weeks** with Claude Code agent graphs, but only after writing about 1,270 component tests first, and again because it had "overridden nearly all of MUI's style defaults" ([Ambrook](https://ambrook.com/engineering/ai/migrating-fast-with-agent-graphs-design-system-material-ui-base-ui)). coder/coder estimated 5.5–8 weeks for 220 MUI files, then closed the epic "in favor of more granular handling" ([coder #18993](https://github.com/coder/coder/issues/18993)). Swizec abandoned an AI-driven JoyUI→MUI rewrite because "we got the same mess as before but in a new library" ([Swizec](https://swizec.com/blog/agents-change-the-math-on-big-bang-migrations)). No team reported reverting from shadcn to MUI, and no Hebrew-specific migration report exists.

Scaling coder's per-file estimate to 36 files gives roughly a week of mechanical work. Theming the five palettes, RTL QA on every overlay, rebuilding the pinned softphone dock and setting up screenshot baselines push a realistic total to **about 1.5–3 weeks**. That figure is an inference from the case studies, not a reported number. The cost is affordable. The question is what the users would gain, and for non-technical staff the answer is roughly nothing they would notice. The adoption trend does not change that. shadcn's CLI went from **1.9M to 55M monthly downloads** between October 2025 and October 2026, but MUI also grew **65% to 45.7M** (npm registry, `api.npmjs.org`, queried 2026-11-12), and State of React 2025 still ranks **MUI first by usage, with shadcn "on the verge of overtaking it"** ([State of React 2025](https://2025.stateofreact.com/en-US/libraries/component-libraries/)). Much of shadcn's download count reflects AI-builder sandboxes rather than distinct teams. MUI is not a dying bet.

## What to do now, and the migration plan if the answer changes

**Do now (about 2–4 days, AI-assisted).** First, remove the dead Tailwind layer: the three `@tailwind` directives, `tailwind.config.js`, `tailwindcss-animate` and the PostCSS entry. No component uses a Tailwind class, and the preflight reset only creates a risk of clashing with MUI. Run a Playwright screenshot pass before and after to confirm nothing moved. Second, upgrade `@mui/material` and `@mui/icons-material` from 7 to 9 with the official codemods ([Upgrade to v9](https://mui.com/material-ui/migration/upgrade-to-v9/)), and swap `stylis-plugin-rtl` for the official `@mui/stylis-plugin-rtl` used in MUI's RTL guide. Third, make AI assistants reliable on MUI: add `@mui/mcp` to Claude Code (`claude mcp add mui-mcp -- npx -y @mui/mcp@latest`) and add a CLAUDE.md rule along the lines of "MUI v9 only; use theme tokens, not hard-coded colors in `sx`; Grid uses `size`; set `dir` on portals; pick Drawer anchors from `isRTL`". Finally, when pasting v0 or Lovable output, ask Claude Code to convert it to MUI components and theme tokens rather than adding Tailwind back.

**Revisit triggers.** Reconsider shadcn if most new screens start in v0, Lovable or Figma Make, if the team finds itself overriding most MUI defaults to reach a custom look, or if MUI's next major drops Emotion and forces a styling rewrite anyway.

**If migrating, do it incrementally.** First, take Playwright screenshot baselines in he/en for all five themes and both drawers. Second, move to Tailwind v4 and initialise shadcn on the **Base UI** base with `--rtl`, which avoids Radix's direction and live-region problems. Third, make the five themes CSS variables that both shadcn and `createTheme` read, and wrap MUI in `StyledEngineProvider enableCssLayer` so the two coexist without `!important` ([MUI Tailwind v4 guide](https://mui.com/material-ui/integrations/tailwindcss/tailwindcss-v4)). Fourth, set touch-size defaults of 40–44px for the button and input variants. Fifth, apply Thrive's rule: new screens use shadcn, and any MUI screen you touch gets migrated. Go leaf-first (buttons, chips, inputs), then the inbox list and chat, and save the Drawers and softphone dock for last, since that is where RTL and physical-anchor behaviour is most fragile. Finally, delete MUI and Emotion in one PR and treat `src/components/ui/*` as protected files in CLAUDE.md. Set a finish date. A migration left at 60% is worse than either library on its own.

## Conclusion

The question is less "which library is better in 2026" and more "which costs this app less". On that measure, MUI wins now and shadcn wins only if the team's design workflow moves into AI generators. The more useful finding is that the app's real liability is neither library: it is the leftover Tailwind layer that ships a conflicting CSS reset and invites AI agents to mix two styling systems. Removing it and upgrading to MUI 9 delivers the "one system, simple" outcome the user wants in a few days. A shadcn migration would deliver the same outcome in a few weeks, with new RTL edge cases to find. Because MUI 9 and shadcn now share Base UI under the hood, the cost of switching later is falling, so waiting carries little penalty.
